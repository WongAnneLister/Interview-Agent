## 范围

要做：

1. 面试结束后的后台任务：基于全部转写重新评定每个能力项（不平均实时分数）；每道题给回答摘要、优点、缺失要点、改进后的参考说法；总体总结与 3 条最优先的改进建议。
2. 复用证据校验；没有有效证据的能力项标为“未考察到”（score 为空）。
3. 按题并发调用（并发上限可配），目标 60 秒内完成；失败可重试；状态 pending / ready / failed。
4. `GET /api/interviews/{id}/report`；报告底部固定声明“AI 生成，仅供练习参考”。
5. 单元测试：假 LLM 下的完整生成、伪造证据处理、并发与重试、状态流转。

不做：前端报告页（PR-25）、录音时间点跳转（PR-35）、表达反馈 R4（口头禅、时长统计）、多次评分取中位数（PR-22 评测时看稳定性再定）、任务队列（Arq/Celery，v0 用进程内后台任务）。

## 总体流程

```text
面试进入 ended
  └─ orchestrator._finish_ended → on_ended → report.request_report(interview_id, user_id=…)
        └─ 立即返回；在 ReportRunner 里 create_task(generate_report(...))
              1. 写/重置 reports 行：status=pending
              2. 读 plan、turns（短会话）
              3. 按题并发：每道“被问到且候选人答过”的题调一次 llm_eval（report_question 提示词）
                 → 证据校验 → 写 evaluations(phase=final)
              4. 汇总：一次调用（report_summary 提示词）给能力项结论、总体总结、3 条建议
                 → 能力项得分由代码从各题 final 分数计算（见下）
              5. 写 reports：status=ready、summary_json、model、prompt_version、generated_at
              任一步彻底失败 → status=failed（summary_json 写错误类型，不写原话）
```

### 为什么按“题”调用，而不是按“能力项”

计划里每道题只属于一个能力项（`Question.competency`），一道题的问答就是这道题全部 turn。按题调用可以并发、单次输入短、失败只影响一题。能力项得分由代码汇总，不让模型再算一遍，结果确定、可测。

## 模块与接口

### 1. 提示词（新增 2 个文件，`role: eval`，version 1）

`prompts/report_question.md` — 一道题的最终评定：

- system：沿用 `evaluate_answer.md` 的评分标准表和证据规则（逐字引用、标 turn_id、至少 4 个字、没证据 score 为 null、不能引用面试官）。加上：这是面试后的最终评定，不受面试中是否追问影响；参考说法要基于候选人自己的经历改写，不编造候选人没说过的项目或数字，可以用“（补充具体数据）”这类占位。不评价口音、音色、年龄、性别。
- user：题目与能力项（`as_data("question")`，格式同 `evaluator._question_data` 但不需要“备选追问方向”）；本题全部问答（`as_data("transcript")`，格式 `turn_id | 面试官/候选人 | 文本`）；`evidence_feedback` 为真时提示“上一次的引用在候选人原话里找不到”。
- 输出 JSON（Pydantic `QuestionReviewDraft`）：
  ```text
  score: int | None (1–5)
  evidence: [{turn_id, quote}]
  summary: str            # 候选人回答摘要，1–3 句
  strengths: list[str]    # 优点，可以为空
  missing_points: list[str]
  improved_answer: str    # 改进后的参考说法
  ```

`prompts/report_summary.md` — 整场汇总：

- 输入只给**代码算好的结构化结果**，不给转写全文：每个能力项（名称、描述、权重、代码算出的得分或“未考察到”）、每道题（题目、能力项、得分、摘要、缺失要点）。这样汇总调用短、不会引入新证据，也不需要再校验引用。
- 输出 JSON（`ReportSummaryDraft`）：
  ```text
  competencies: [{name, conclusion}]   # 每个能力项一句结论；名称必须与输入完全一致
  overall: str                         # 总体总结，3–5 句
  top_improvements: list[str]          # 恰好 3 条，按优先级
  ```
- 用 Pydantic 校验器检查：`top_improvements` 长度为 3；`competencies` 的名称集合等于输入的名称集合（通过 `generate_structured(..., context=...)` 传入期望的名称，校验器从 `info.context` 读）。校验失败走 `generate_structured` 自带的最多 2 次重试。

写完两个提示词后运行 `make prompts-lock`，把 `prompts/versions.lock` 一起改掉（`make check` 会检查）。

### 2. `domain/report.py`

```python
REPORT_DISCLAIMER = "AI 生成，仅供练习参考，不代表任何企业的录用判断。"

class ReportSettings 相关配置见第 4 节

class QuestionReview(BaseModel):          # 写进 summary_json 和返回给前端
    question_id: str
    question: str
    competency: str
    asked: bool                             # 没被问到的题 asked=False，其余字段为空
    score: int | None
    evidence: list[EvidenceQuote]
    summary: str
    strengths: list[str]
    missing_points: list[str]
    improved_answer: str

class CompetencyReview(BaseModel):
    name: str
    weight: float
    score: float | None                     # None = 未考察到
    conclusion: str
    evidence: list[EvidenceQuote]           # 来自该能力项各题的有效证据

class ReportBody(BaseModel):              # summary_json 的结构
    schema_version: Literal[1] = 1
    overall_score: float | None             # 有分能力项按权重加权平均，保留 1 位小数
    overall: str
    top_improvements: list[str]
    competencies: list[CompetencyReview]
    questions: list[QuestionReview]
    disclaimer: str = REPORT_DISCLAIMER
    degraded: list[str]                     # 降级说明，例如 "q3: 评分失败"，没有则为空

async def review_question(llm, question, competency, turns, *, interview_id) -> QuestionReviewResult
async def generate_report(*, interview_id, user_id, sessionmaker, providers, settings) -> None
async def request_report(interview_id, *, user_id) -> None   # 保留现有签名，见第 3 节
```

`review_question`（对照 `evaluator.evaluate` 写，可以抽公共函数但别改 `evaluate` 的行为）：

- 调 `generate_structured(llm, 渲染好的 report_question, QuestionReviewDraft, max_tokens=…, timeout_s=settings.question_timeout_s)`。
- 用 `evaluator.validate_evidence(draft.evidence, turns)` 校验。**有分但没有有效证据时，带 `evidence_feedback=True` 重试一次**，重试调用包在 `marked_retry()` 里（C3）。
- 仍然没有有效证据：score 置空（未考察到），evidence 为空，摘要等文字字段保留。
- 返回值里带实际厂商、型号、`prompt_id@version`、耗时、重试次数（C10：切到备用时记的是备用）。
- 开 span `report.question`，属性：`interview_id`、`question.id`、`report.evidence_kept`、`report.evidence_dropped`、`report.score_nulled`、`report.retries`。

`generate_report`：

1. 短会话：取或建 `Report` 行，置 `status=pending`、清空 `summary_json`、`generated_at`。用 `UserScopedRepository`（照 `orchestrator_store.TurnRepository` 写一个 `ReportRepository`）。
2. 短会话：读 plan（`plan_from_row`）和全部 turns（按 seq）。按 `question_id` 分组成 `TranscriptTurn` 列表；**只评有候选人发言的题**，其余题 `asked=False`。
3. 按题并发：`asyncio.Semaphore(settings.concurrency)` 限并发，`asyncio.gather` 跑全部题。每题失败（`ProviderError`、`StructuredOutputError`）**整题重试**最多 `settings.question_attempts - 1` 次；仍失败则该题 score 为空、`degraded` 加一条，不让整份报告失败。
4. 每题结果写一条 `Evaluation(phase=FINAL)`：`turn_id` 取本题最后一条候选人发言，`score`、`evidence_json`、`detail_json`（summary、strengths、missing_points、improved_answer、latency_ms、retries、evidence_dropped、evidence_retried）、`model="{provider}/{model}"`、`prompt_version`。写之前先删掉这场面试已有的 `phase=FINAL` 记录（重新生成时不重复）。`next_action` 为空。
5. 能力项得分（代码算，不问模型）：同一能力项下有分的题取**算术平均**，保留 1 位小数；一题都没有分则为 None（未考察到）。`covered=False` 的能力项也列出来，score 为 None。**不读 phase=live 的实时分数**（PRD：最终得分重新评定）。
6. 汇总：调一次 `report_summary`。失败（重试用尽）时降级：结论用固定文字（有分：“得分 X 分，详见各题反馈”；无分：“本场未考察到”），`overall` 用固定文字，`top_improvements` 取得分最低的 3 道题的第一条缺失要点（不够 3 条就少给），`degraded` 加一条。汇总失败不让报告失败。
7. 写 `reports`：`status=ready`、`summary_json=ReportBody.model_dump(mode="json")`、`model`（汇总调用的 `provider/model`，汇总降级时取第一道题的）、`prompt_version`（`report_question@1+report_summary@1` 这种组合）、`generated_at=func.now()`。
8. 只有“读不到 plan / 数据库写失败 / 未预料的异常 / 所有被问到的题都失败”才置 `status=failed`，`summary_json={"error": 错误类型名}`。
9. 整个流程包在 `asyncio.timeout(settings.total_timeout_s)` 里；超时按第 8 步失败处理。
10. 开 span `report.generate`（interview_id、`report.questions`、`report.degraded`、`report.duration_ms`）；Prometheus：`report_generated{status}` 计数、`report_duration_seconds` 直方图（桶 5、10、20、30、45、60、90、120）。
11. 日志：`report_ready` / `report_failed`，只记 interview_id、题数、耗时、降级数、错误类型；**不记摘要、参考说法、引用原话**。

模型取法：`providers.llm("llm_eval", CallContext(user_id=…, interview_id=…, usage_role=UsageRole.REPORT))`，每道题一个 CallContext（turn_id 填本题最后一条候选人发言）。没配置时（`ProviderNotConfigured`）报告直接 failed。

### 3. 触发方式：进程内后台任务

`on_ended` 在编排器锁里被 await，**不能在里面等报告生成完**。做法：

- 新增 `class ReportRunner`（放在 `domain/report.py`）：持有 `sessionmaker`、`providers`、`settings`，`start(interview_id, user_id)` 用 `asyncio.create_task` 启动 `generate_report` 并登记到 `self._tasks`（完成后移除，照 `InterviewOrchestrator._track`）；同一场面试已有任务在跑时不重复启动；`aclose()` 等所有任务结束（上限 `settings.total_timeout_s`），超时就取消。
- `api/resources.py`：`Resources` 增加 `reports: ReportRunner | None = None` 字段；`create_resources` 创建它；`Resources.close()` 先 `await reports.aclose()` 再关 providers 和数据库。
- `request_report` 改成接收 runner：`async def request_report(interview_id, *, user_id, runner: ReportRunner | None) -> None`，runner 为空时只记 warning。`text_ws.py` 的 `on_ended` 传 `resources.reports`。测试里 `monkeypatch.setattr(report, "request_report", ...)` 的写法要跟着更新（`test_text_ws.py`）。
- 进程重启会丢掉正在生成的报告：报告停在 pending。本 PR 不做重新调度，记进 challenges（见“文档”）。GET 接口里 pending 超过 `total_timeout_s × 2` 的报告视为卡住，返回时 status 报 failed（只改返回值，不写库）；前端再用 POST 重新生成。

### 4. 配置（`config.py` 新增 `ReportSettings`，前缀 `REPORT_`，同步 `.env.example` 并写清用途）

| 字段 | 默认 | 用途 |
|---|---|---|
| `concurrency` | 4 | 同时评定几道题 |
| `question_timeout_s` | 40 | 单题一次调用的超时（max 开思考较慢） |
| `question_attempts` | 2 | 单题最多尝试几次（含第一次） |
| `total_timeout_s` | 90 | 整份报告的上限，超时 failed |

`Settings` 加 `report: ReportSettings`，给默认值（`Field(default_factory=...)`），这样 `tests/unit/test_api.py` 的 `make_settings` 不用改。
`load_settings()` 是逐组手写读取的，要同时加一行 `report = _load(ReportSettings, env_file, errors)` 并传给 `Settings(...)`，否则 `.env` 里的 `REPORT_*` 不会生效；`tests/unit/test_config.py` 加一个用例确认能从环境变量读到。

能力项名称校验的写法参考 `domain/plan.py` 的 `validate_with_context`（`ValidationInfo.context`）。

### 5. 接口 `api/routes/interviews.py`

- `GET /api/interviews/{interview_id}/report` → `ReportOut`：
  ```text
  interview_id, status (pending|ready|failed), generated_at, model, prompt_version,
  report: ReportBody | None   # ready 时才有
  error: str | None           # failed 时的错误类型
  disclaimer: str             # 恒为 REPORT_DISCLAIMER，pending / failed 也返回
  ```
- 面试不存在或不属于该用户：404（照 `_owned_interview`）。面试没结束、也没有报告行：404 `report_not_found`，message “面试结束后才会生成报告”。
- `POST /api/interviews/{interview_id}/report`：面试已结束（completed / aborted）且报告是 failed 或不存在时重新生成，返回 202 和当前 ReportOut（pending）；pending 时 409；ready 时 409（不覆盖已有报告）。
- 两个路由都依赖 `CurrentUserId`（`test_every_business_route_requires_user` 会检查）。

## 测试（`tests/unit/test_report.py`，全部假厂商 + SQLite，照 `test_orchestrator.py` 的 harness）

需要 mock 的：`usage.record_usage`（C12）。用一个按提示词 id 分发回复的假 LLM（看 system 消息内容区分 report_question / report_summary）。

1. **完整生成**：seed 一场 4 题、5 条候选人回答的面试（可以直接写 turns，不必跑编排器）。生成后：status=ready、generated_at 有值；每道被问到的题一条 `phase=final` 的 Evaluation；`summary_json` 能还原成 `ReportBody`；`disclaimer` 正确；`top_improvements` 3 条；能力项得分 = 各题平均。
2. **伪造证据**：某题模型第一次给的引用在原话里不存在 → 重试一次（`evidence_retried`）；第二次仍伪造 → 该题 score 为空、evidence 为空，对应能力项（只有这一题时）为“未考察到”（score None）。另一个用例：第二次给了真引用 → 保留分数。
3. **引用面试官的话**不算证据（`validate_evidence` 已处理，这里确认没被绕过）。
4. **未被问到的题**：`asked=False`，不调用模型（假 LLM 调用次数确认）。
5. **不用实时分数**：seed 几条 `phase=live` 的 Evaluation（分数故意和 final 不同），报告得分只取 final。
6. **并发上限**：假 LLM 带 `first_token_delay_s`，记录同时进行的调用数峰值，等于 `concurrency`（设成 2）。
7. **单题重试**：某题第一次抛 `ProviderTimeout`、第二次成功 → 报告 ready，该题有分；两次都失败 → 报告仍 ready，该题 score 为空，`degraded` 有一条。
8. **全部题失败 / 没配置 llm_eval / 总超时**：status=failed，`summary_json["error"]` 是错误类型名。
9. **汇总失败降级**：report_summary 一直返回非法 JSON → 报告 ready，结论是固定文字，`degraded` 有一条，`top_improvements` 来自最低分的题。
10. **汇总能力项名称校验**：模型漏掉一个能力项 → 触发 `generate_structured` 的重试。
11. **重新生成**：生成两次，`phase=final` 的 Evaluation 不重复。
12. **ReportRunner**：`request_report` 立即返回（任务还没完成时就返回）；同一场重复请求只跑一个任务；`aclose()` 等任务结束。
13. **API**：GET 在 pending / ready / failed 三种状态的返回；别人的面试 404；面试未结束 404；pending 超时视为 failed；POST 重新生成的 202 / 409。
14. **日志不含原话**：用 `structlog.testing.capture_logs`，确认日志里没有候选人回答和参考说法的文字（照 `test_logs_do_not_contain_dialogue`）。
15. 更新 `test_text_ws.py`：面试结束后 `request_report` 被调用（runner 参数）。

live 测试（`tests/live/test_report_live.py`，`@pytest.mark.live`，默认不跑）：用真实 `llm_eval` 对一场固定 fixture 生成报告，打印每题耗时和总耗时，断言 60 秒内完成、所有证据都通过校验。**不要自己跑**，在汇报里提醒我手动跑 `make test-live`。
