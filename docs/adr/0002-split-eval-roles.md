# ADR-0002 面试中的实时评估与面试后的报告评估分开配置模型

- 状态：已接受（2026-10-19）
- 相关：PRD“双层 agent 的协作方式”“延迟预算”，[实测结论](../benchmarks/findings.md)，
  [challenges.md C1](../challenges.md)

## 背景

PRD 规定后台评估器异步运行：前台先说过渡语，评估器要在 **2.5 秒内**给出“追问还是换题”，
超时则前台按面试计划提下一题，评估结果只用于评分。PRD 同时规定：面试中的实时评分只用于决定追问，
报告里的最终得分在面试结束后基于全部转写重新评定（报告 60 秒内生成）。

原来只有一个评估角色 `llm_eval`（qwen3.8-max），简历解析、JD 解析、出题、实时评估、报告都用它。

2026-10-18 用评估器的真实提示词和输出（约 290 token）实测 `evaluate()` 完整耗时（`tests/live/test_evaluator_live.py`）：

| 型号（关思考） | P50 | P95 | 备注 |
|---|---|---|---|
| qwen3.8-max | 6.2 秒 | 7.7 秒 | 开思考更慢（结构化输出约 14.7 秒） |
| qwen3.8-flash | 约 8.3 秒 | — | 输出更啰嗦，追问方向常照抄要点，评估直接失败 |
| deepseek-flash | 2.2 秒 | 3.9 秒 | 15 次中 6 次因追问方向含要点原文触发格式重试，每次多约 1.5 秒 |

三家首 token 都在 0.6–0.75 秒，差距在出字速度：每个输出 token 百炼 14–18 ms，DeepSeek 约 4 ms。

## 决策

1. **新增实时评估角色 `llm_live_eval`**（`LLM_LIVE_EVAL_*`），用 **deepseek-flash 关思考**，超时 10 秒。
   `ProviderRegistry.live_eval_llm()` 取这个角色；没配置时回退到 `llm_eval`，不影响只配了旧角色的环境。
2. **`llm_eval` 保持 qwen3.8-max**，用于简历解析、JD 解析、出题，以及以后的报告评估（PR-21）。
   这些步骤不在对话链路上，不需要关思考，`.env` 里原先的临时关思考已去掉。
   原计划另拆 `llm_report` 角色，现在不需要：重质量的工作都留在 `llm_eval`。
3. **追问方向泄露要点时不重试**：模型给的 `follow_up_focus` 含要点原文，代码直接改成 `next_question` 并清空 focus，
   与“追问已达上限”的处理方式一致（`EvaluationResult.override_reason` 区分两者，Prometheus 计数 `evaluator_action_overridden`）。
   结果确定，也省掉一次调用；代价是这一轮少一次追问。
4. 实时评估的 JSON 仍把 `next_action` 放在第一个字段，留着以后需要时做流式提前决策；目前不需要。
5. 最终报告固定用一个型号评分；结果对象记录实际作答的厂商和型号（challenges C10），切到备用时在报告里标明。

## 结果

改完后同一测试再跑 35 次（2026-10-19）：P50 2.0–2.1 秒，P95 2.3–2.7 秒，最慢 2.7 秒，格式重试 0 次；
20 次里 1 次因泄露要点被改成换题。P95 已接近 2.5 秒，PR-19 的 2.5 秒等待上限下大部分轮次能赶上。

## 后果与待验证

- 实时评估和最终评分由不同厂商给出，给分水平不同（同一段回答 max 给 4 分，deepseek-flash 多为 3 分）。
  实时分数不对外展示，只用于决定追问；报告评分仍以 `llm_eval` 为准。PR-21 要测一下两者的一致性。
- 实时评估的主模型在 DeepSeek，DeepSeek 不可用时会切到 `LLM_FALLBACK_*`。目前备用也是 deepseek-flash，
  起不到容灾作用；PR-19 之前考虑把实时评估的备用改成百炼 max（会超时降级，但评分结果仍能入库）。
- 少数轮次仍会超过 2.5 秒，这时按计划换题（PR-19 实现降级并计数），属于设计内的行为。
